# Architecture

The shape of the codebase. Read this *after* `glossary.md` (vocabulary) and `flows.md` (what the app does), and *before* changing anything load-bearing.

This doc is deliberately short. It captures the wiring that isn't obvious from reading individual files; everything else is in glossary / flows / merge-points.

---

## Provider stack

```
DatabaseProvider                  ← migrations, seed, one-time migrations, foreground tasks
  └── DataRefreshProvider         ← invalidation hub; pure state
        └── ThemeProvider         ← reads DB on mount; resolves accent + light/dark
              └── PrivacyProvider ← reads DB on mount; hide/random toggles
                    └── AppStack  ← Stack of routes; renders BackupSetupModal
```

**Order is load-bearing.**
- `DatabaseProvider` must be outermost: `ThemeProvider` and `PrivacyProvider` query the DB on mount.
- `BackupSetupModal` is rendered *inside* `AppStack` (which is inside `ThemeProvider`) because the modal calls `useTheme()`. The setup state lives in `DatabaseContext` and is forwarded down. Rendering the modal as a sibling of `DatabaseProvider`'s children would crash with `useTheme must be used within ThemeProvider` — that was the bug fixed in v1.8.1.

`DataRefreshProvider` doesn't read the DB; it could be anywhere above the screens, but currently sits between Database and Theme so theme reloads (a low-frequency case) can listen to its `themes` revision if they ever need to.

## Data flow on a mutation

Every user-driven mutation follows this shape:

1. **Screen** (e.g. `src/app/transaction/form.tsx`) collects form state.
2. **Query function** (e.g. `createTransaction` in `src/db/queries/transactions.ts`) writes to the DB and applies side effects (balance update, link cleanup, currency snapshot capture).
3. Where the change spans tables, the screen wraps the work in a SQLite `BEGIN TRANSACTION` / `COMMIT` / `ROLLBACK` so partial failure can't desync data.
4. Screen calls `invalidate("entityA", "entityB", ...)` from `useDataRefresh()`.
5. Hooks subscribed to those entity revisions (`useAccounts`, `useTransactions`, etc.) re-query and re-render.
6. The component tree updates with fresh data.

**Forgetting `invalidate(...)` is the most common bug surface.** Screens read stale until something else triggers a refresh. The full list of entities and what bumps each is in `glossary.md` under "DataRefresh entities".

## Migrations

Two-source pattern. Both are checked in:

- **`src/db/migrations/NNNN_*.sql`** — the human-readable migration source. Generated by `drizzle-kit generate` from schema changes; can also be hand-written for surgical changes that drizzle-kit can't infer (e.g. data backfills, drop-table cleanups).
- **`src/db/migrations/migrations.js`** — the runtime-loaded inlined migrations. Metro can't `require()` a `.sql` file, so each SQL is template-literal-embedded here. The journal at the top mirrors `drizzle-kit`'s state.

When changing the schema:
1. Edit `src/db/schema/*.ts`.
2. `npx drizzle-kit generate` to produce the next `.sql` file (interactive — needs a TTY).
3. Open the new `.sql`, copy each statement, and add an `mNNNN: \`...\`` entry to `migrations.js`'s `migrations` block. Add a corresponding entry to the journal at the top.
4. Verify the on-device upgrade path (an existing DB should run only the new migration).

For hand-written migrations (no `drizzle-kit generate`): write the `.sql` and the inline together — keep them in sync. The runtime only reads the inline; the `.sql` is for humans and version control.

> **The FK trap**: `expo-sqlite` runs with `PRAGMA foreign_keys = OFF` by default. Schema FK clauses *exist* but are *not enforced* at runtime. Where referential integrity matters (deleting an account that still has transactions, deleting a category with child subcategories), the guard lives in code, not the schema. Don't trust FKs to protect anything; check explicitly in the query layer.

## One-time data migrations

Drizzle migrations only do schema. Data backfills + semantic flips live in `src/providers/DatabaseProvider.tsx`, gated by idempotent flags in the `settings` table:

| Flag                       | Purpose                                                |
| -------------------------- | ------------------------------------------------------ |
| `credit_balance_migrated`  | v1.0.1 flip from "balance = debt" to "balance = available credit" |
| `default_themes_seeded`    | First-launch insert of 4 default themes                |
| `txn_currency_backfilled`  | Phase-2 fill of `transactions.currency` from accounts  |

Pattern for a new one-time migration:
1. Add a function in `DatabaseProvider.tsx` that early-returns when the flag is set.
2. After the work, insert the flag with `onConflictDoNothing` so reruns are no-ops.
3. Wire it into the boot pipeline `useEffect` chain *after* `seed()` and any schema migration that introduces the columns it touches.
4. Document the flag in `glossary.md` under "Settings keys".

## Boot pipeline (`DatabaseProvider`)

```
schema migrations (drizzle)
  → seed()                              ← default categories, subcategories, settings
  → migrateCreditCardBalances()         ← gated by credit_balance_migrated
  → seedDefaultThemes()                 ← gated by default_themes_seeded
  → backfillTransactionCurrency()       ← gated by txn_currency_backfilled
  → setIsSeeded(true)
    → check backup_setup_done
      → if missing: render BackupSetupModal, block here
      → if set: continue
        → processDueRecurring()         ← creates due recurring transactions
        → applyInvestmentInterest()     ← daily compounding
        → checkAndRunAutoBackup()       ← if not yet backed up today
        → checkAndFetchRates()          ← if multi-currency + cache stale
```

Foreground tasks are fired in parallel (each as its own unawaited promise inside the same `useEffect`); the screen is allowed to render as soon as the gate clears. They don't block each other and the order between them is not load-bearing.

## File organization (high level)

- **`src/app/`** — Expo Router screens. File path = route. `(tabs)/` = bottom tabs; bracketed `[id]` = dynamic param; modals are declared in `_layout.tsx` with `presentation: "modal"`.
- **`src/components/`** — atomic design layers. Atoms = primitives, molecules = small composites, organisms = feature-level (forms, pickers), templates = layout shells (`ScreenLayout`, `ModalLayout`, `HeaderBar`).
- **`src/db/`** — schema, queries, migrations, seed. *The only place that imports `drizzle-orm` directly.* Screens go through query functions, not raw drizzle.
- **`src/providers/`** — global state contexts. New global state = new provider. Don't sprinkle context creation across feature folders.
- **`src/services/`** — side-effect-heavy code that touches the world (filesystem, network, device APIs). Pure data transforms live in `utils/`.
- **`src/hooks/`** — query hooks that subscribe to `DataRefresh` revisions and re-fetch. One per entity.
- **`src/theme/`** — color palettes, typography, spacing tokens. `useTheme()` consumers read from here via the provider.
- **`src/i18n/`** — i18next config + locale JSON. Add a new key in all 5 locales at once.
- **`src/constants/`** — pure data: currencies, palette colors, FAB actions, default categories, default settings.
- **`src/plugins/`** — Expo config plugins (release signing).
- **`src/utils/`** — pure transforms (formatting, date arithmetic, amount input helpers). No side effects.

## Where to look for X

| Task | Start here |
| --- | --- |
| Add or rename a domain term | `docs/glossary.md` |
| Add a new user-facing flow | `docs/flows.md` |
| Touch the transaction form | `docs/merge-points.md` § Transaction form |
| Add a new account type | `src/types/enums.ts` (`AccountType` union) → `src/db/schema/accounts.ts` (`type` column comment) → `src/db/queries/accounts.ts` (`getAccountsTotals` classification block) → `src/components/organisms/AccountForm.tsx` (field switch by type) → `src/app/account/[id].tsx` (action buttons by type) → `src/i18n/locales/*.json` (`accounts.<type>` label, all 5 locales). Then grep for `type === "credit"` etc. to find every other type-filtered call site and decide whether the new type belongs there |
| Add a new transaction type | `src/types/enums.ts` (`TransactionType` union) → `src/db/queries/accounts.ts` (`updateAccountBalance` delta direction) → `src/components/organisms/TransactionForm.tsx` (mode switch + field reveal) → `src/i18n/locales/*.json` (`transactionForm.*` labels). Most of the form already branches on type — extend the switch, don't rewrite the form |
| Add a new screen | create file under `src/app/...`; register in `src/app/_layout.tsx` (or `(tabs)/_layout.tsx` for tabs); add i18n keys; add to `flows.md` |
| Add a new entity (table) | schema → migration (`drizzle-kit generate` + inline) → query module → hook → `DataRefreshProvider` entity key → backup service export/restore lists → `invalidateAll` helper in `src/app/settings/backup.tsx` → `glossary.md` DataRefresh table → `merge-points.md` § restore touch radius |
| Add a new setting | `getSetting`/`setSetting` to read/write; default in `src/constants/settings.ts` if applicable; UI row in `src/app/settings/index.tsx`; entry in `glossary.md` Settings table |
| Add a new one-time data migration | function in `DatabaseProvider.tsx`, gated by a settings flag; chain into the boot pipeline `useEffect`; document the flag in `glossary.md` Settings table; see § "One-time data migrations" above |
| Investigate an aggregate showing the "≈" or "missing rates" banner | `convertRow` in `src/db/queries/transactions.ts` and the `CurrencyConverter` in `src/services/exchangeRate.service.ts`; conceptually documented in `glossary.md` § Currency snapshot fields |
| Diagnose "balance + transactions row got out of sync" | the edit path in `src/app/transaction/form.tsx` and `updateAccountBalance` in `src/db/queries/accounts.ts`. The atomic `BEGIN/COMMIT/ROLLBACK` is the safety net; if it's bypassed (e.g. a new mutation path skipped the wrap), that's where the bug lives |

## When to update which doc

When you ship a change, ask:

| Did the change... | Update |
| --- | --- |
| Add/rename a screen, action, gesture, or smart default? | `flows.md` |
| Add/rename an account type, transaction type, settings key, refresh entity, or error class? | `glossary.md` |
| Change an invariant or computation rule? | `glossary.md` (and add a `// invariant:` comment at the site) |
| Change provider order, migration scheme, or boot sequence? | `architecture.md` |
| Add or remove a place where many flows converge (a new form, a new central service)? | `merge-points.md` |
| Change visual style only? | nothing |
| Refactor without behavior change? | nothing (the docs describe behavior, not implementation) |
